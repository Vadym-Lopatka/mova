# Conformance deviations

`tests/conformance_test.rs` replays every form in `tests/conformance/corpus/
*.corpus` through mova and diffs the result against the adjacent `*.golden`
file (real Clojure output, generated by `tools/gen-golden.bb`, which shells
out to a real JVM `clojure` process pinned to
`tests/conformance/CLOJURE_VERSION` (1.13.0-alpha6) -- one `clojure`
process per corpus file; see `tools/jvm-runner.clj`). Any mismatch must be
either a genuine mova bug (fix it!) or an intentional, documented
deviation listed here.

A golden line is `OK<TAB><pr-str>` or `ERR<TAB><ExceptionSimpleName>` (a
bare `ERR` with no kind is also still accepted, for backward
compatibility with stale goldens). The recorded kind is Clojure's own
exception class simple name; `tests/conformance_test.rs` currently
compares exceptions by occurrence only (mova has no exception-class
taxonomy yet -- that's milestone M8's job), carrying the kind forward as
data for when that comparison goes live -- see that file's
`COMPARE_EXCEPTION_KIND` for the staged flag.

## How this file is read

The test parses this file for lines starting with `|`, splits each on `|`,
and treats a row as a deviation entry when its second column parses as a
plain integer (the header/separator rows don't, so they're skipped for
free -- the parser is deliberately dumb, per PLAN.md). Columns, in order:

| file | line | form | clojure | mova | why |
|------|------|------|---------|-------|-----|

- **file**: corpus file basename (e.g. `numbers.corpus`).
- **line**: 1-indexed line number *in that corpus file* (comments/blank
  lines count toward line numbers, since they're real lines in the file --
  only the position of the form's own line matters).
- **form / clojure / mova / why**: human context; not parsed, but kept
  accurate so this table is useful on its own.

A mismatch at a whitelisted `file:line` passes (and is counted). The test
also asserts every whitelisted `file:line` still actually mismatches --
a "fixed" entry left behind here would silently stop being exercised, so a
stale entry fails the test until removed.

## W-ERR: `catch` is total on a bare thrown value; `instance?` deliberately stays narrower

Field report from a host application (a real embedding client): `(catch Exception e ...)`/
`(catch Throwable e ...)`, the JVM-idiomatic way to guard foreign/plugin
code, used to silently fail to catch a bare thrown non-`Throwable` value
(`(throw 42)`, `(throw :boom)`, a thrown string, ...) -- the process-
killing hole every embedder using that idiom had. W-ERR fixed it: such a
value now classifies under the same generic `java.lang.RuntimeException`/
`java.lang.Exception`/`java.lang.Throwable` tail every unclassified
internal error already gets (`eval::special_forms::
thrown_value_class_chain`), so a typed `Exception`/`Throwable` catch is now
TOTAL -- nothing mova can throw escapes it.

`instance?` was deliberately NOT changed to match: `(instance? Exception
42)` still answers `false`, same as before. This is a genuine, now-more-
visible asymmetry -- `catch`'s "should this be handled as if it derives
from Exception/Throwable" question and `instance?`'s "is this actually
shaped like one" question no longer agree for a bare thrown value -- but
real Clojure has no scenario to measure this against at all: `throw`
requires its argument to already BE a `Throwable` there, so
"`(instance? Exception <bare-non-Throwable-value>)`" is not a form real
Clojure can even evaluate without throwing first. There is no oracle
answer to conform to; widening `instance?`'s exception-membership
predicate (`hostclass::is_exception_named`) to also answer `true` for
arbitrary non-`Inst` values would go beyond making `catch` total into
inventing JVM behavior that was never measured, and was explicitly ruled
out of this wave's scope. Flagged here as a disclosed, deliberate gap for
a future wave to pick up if a real caller needs `instance?`-based dispatch
over the same total set `catch` now covers.

## S5 (SPEC-numtower): what the numeric tower closed, and the two gaps it did not

`(= 1 1.0)` used to be the first row of the table above (`numbers.corpus`
line 29): mova had no ratio type, so `=` blended `Int`/`Float` by numeric
value. S5 gave mova the whole tower and made `=` CATEGORY-STRICT the way
`clojure.lang.Numbers.equal` is (INTEGER / FLOATING / DECIMAL / RATIO),
with the cross-category numeric comparison living in `==` instead. That row
is therefore gone -- `(= 1 1.0)` is now `false` on both sides, and the
harness's own stale-entry check is what forced its removal.

Four divergences remain, written up in the four sections below: the
INT WIDTH gap, the DIVIDE-BY-ZERO MESSAGE gap, the N-ARY IDENTITY FOLD, and
FLOAT IDENTITY IN COLLECTION KEYS. None is representable as a table row
(per this file's own parsing rule, a row must be an ACTUAL corpus-line
mismatch, and no corpus line asserts on any of them). The first two and the
seq-class naming quirk are policed instead by `compat/numtower-check.py`,
which replays the 99-row `compat/numtower-oracle-transcript.txt` and the
367-row `compat/numtower-oracle-transcript2.txt` against the release binary
and fails on any row whose divergence is NOT one of its three whitelisted
kinds -- each whitelist entry additionally asserting that the row's VALUE
is still exactly right, and that a row which starts matching completely is
reported as a stale entry to delete.

### S5 int width: `java.lang.Integer` / `Short` / `Byte` all report as `java.lang.Long`

mova has ONE integer type: `Value::Int` is an `i64`. Real Clojure has
`java.lang.Long` **and** the narrower boxed `Integer`/`Short`/`Byte`, and
`int`, `short`, `byte`, `compare`, `hash` and the `unchecked-*-int` family
all return one of the narrow ones. So mova computes the right NUMBER for
every such form and reports the wrong CLASS:

```
(int 3.99)      => 3   ; real Clojure java.lang.Integer, mova java.lang.Long
(compare 1N 2)  => -1  ; likewise
(hash 7)        => -137604029  ; likewise -- the VALUE is now exact
```

This is not a numeric-tower gap and S5 did not create it (`(class (int 3))`
was already `java.lang.Long` before); the tower work merely made it
countable, because the transcript records a `class` for every row. Closing
it means a second integer `Value` variant threaded through 364 `Value::Int(`
match sites in 33 files, plus the arithmetic rule that an `Integer` operand
still produces a `Long` result -- a change with a far worse
regression-to-benefit ratio than the six rows it buys, and one that would
collide with every other in-flight workstream. `compat/numtower-check.py`'s
`INT_WIDTH_GAP_BY_FILE` lists exactly which rows it covers and asserts each
one is still value-exact AND still class-divergent, so a fix cannot land
unnoticed and a regression cannot hide behind it.

### S5 divide-by-zero message: `"Divide by zero"` vs `"/ by zero"`

Real Clojure's `quot`/`rem` message depends on what its COMPILER inferred:
`(quot 5 0)` written with two `long` literals inlines to Java's own `/`,
whose `ArithmeticException` says `"/ by zero"`, while the boxed
`Numbers.quotient(Object, Object)` path says `"Divide by zero"`. Both are
measured. mova has one path and no primitive type inference, so it always
says `"Divide by zero"` -- which is what the transcript's own rows demand
(`(mod 5 0)` and `(quot 5N 0)`, rows 66-67, both take the boxed path on the
JVM). The two supplement rows that take the inlined path
(`numtower-oracle-transcript2.txt` lines 159-160) are whitelisted in
`DIVZERO_MESSAGE_GAP_BY_FILE`.

## S5 float identity in collection KEYS: `#{0.0}` does not contain `-0.0`

S5 made the `=` FUNCTION conformant for doubles -- `(= 0.0 -0.0)` is true
and `(= ##NaN ##NaN)` is false, both measured, both matching Clojure's
`DoubleOps.equiv` (a plain IEEE `==` on the primitives). That fix reaches
`=`, `not=`, `distinct`, `distinct?`, and element-wise collection equality,
because all of them go through `Interp::values_equal`.

It does NOT reach hash-map/hash-set KEYING, which uses `Value`'s own
`PartialEq`/`Hash` (still bitwise on floats). Measured difference:

| form | real Clojure | mova |
|------|--------------|------|
| `(contains? #{0.0} -0.0)` | `true` | `false` |
| `(get {0.0 :a} -0.0)` | `:a` | `nil` |
| `(get {##NaN :a} ##NaN)` | `nil` | `:a` |
| `(count (set [0.0 -0.0]))` | `1` | `2` |
| `(count (set [##NaN ##NaN]))` | `2` | `1` |

Closing it requires giving `Value` a **non-reflexive** `Eq`: the NaN rows
above are only reproducible if a NaN key genuinely cannot find itself. Rust
(and `imbl`'s `HashMap`/`HashSet`, and every `BTreeMap` ordering in this
crate) treat `Eq`'s reflexivity as a hard precondition, so that is a change
to the persistent-collection layer's contract, not a numeric change, and it
is deliberately out of S5's scope. The `hash` BUILTIN already agrees with
the conformant `=` (`(hash 0.0)` == `(hash -0.0)` == `0`, measured) -- only
the internal key hash still splits them.

## S5 n-ary identity fold: `(+ -0.0 -0.0)` is `0.0`, not `-0.0`

Measured while writing the tower, and NOT introduced by it: mova's n-ary
`+`/`*` natives fold from the operator's identity element, so `(+ -0.0
-0.0)` computes `(0 + -0.0) + -0.0` and yields `0.0`. Real Clojure's
2-arity `+` calls `Numbers.add` directly with no identity step and yields
`-0.0`. The identity step is deliberate and load-bearing in the compiled
tier -- `compile::ir::NumBin::AddFold`/`MulFold` exist to reproduce it, and
`compile::exec`'s float-lane specializations (`FAddFoldFF`/`FAddFoldFI`,
`RF::AddFoldK`/`AddFoldX`) are built on top of it -- so correcting it is a
compiled-tier change, not a native one, and is left to its own workstream.

S5 did narrow it: a fold whose FIRST argument is a tower value now skips the
identity step (`builtins::numbers::skips_identity`, shared with the
compiled tier's `IntrinOp::Add`/`Mul` arms). That was not cosmetic --
under `with-precision` the identity step is an extra ROUNDING, and without
the skip `(with-precision 2 (* 123M 456M))` answered `5.5E+4M` where real
Clojure answers `5.6E+4M`. Measured confirmation that the skip lands mova
on Clojure's 2-arity rather than its 3-arity: real Clojure's
`(with-precision 2 (* 1 123M 456M))` IS `5.5E+4M`.

## M13 (SPEC-M13-EQWITH.md): shared-subtree pruning skips the per-element predicate, so a shared `##NaN` compares equal

`values_equal`'s sequential arm (`List`/`Vector`/`MapEntry`/`Queue`, all
`PVec`-backed) now routes `PVec::Big`-vs-`PVec::Big` pairs through
`champ::PVector::try_eq_by` instead of the manual `len`+`zip` walk
(`src/eval/mod.rs`, `values_equal`). `try_eq_by` descends both tries in
lockstep and, whenever the two sides' node pointers are identical (same
allocation), skips the whole subtree WITHOUT calling the predicate on any
element inside it -- that predicate is `values_equal` itself, recursing,
so a pruned subtree's elements are never compared by Clojure's own
`=` rules (category-strict numerics, `(= 0.0 -0.0)` true, `(= ##NaN
##NaN)` false) at all; they are treated as equal by virtue of being the
identical allocation on both sides.

Measured consequence: build `v2` by editing one element of a 100k-element
`v1` (e.g. `(let [v2 (conj (pop v1) (peek v1))])`, or any edit far from a
shared NaN), such that a NaN elsewhere in `v1` sits inside a subtree
`v2` still shares by pointer. A strict element-by-element walk would call
`values_equal` on that NaN pair and answer `false` (NaN is `=` to
nothing, not even itself); the pruned walk never reaches it, sees the
shared pointer, and counts that subtree equal. So `(= v1 v2)` can be
`true` where a hypothetical fully-strict walk over the same two vectors
would say `false`, whenever the only structural difference between them
lies outside the NaN's shared subtree.

This is not a new kind of unsoundness -- it is the SAME identity-implies-
equal reasoning Clojure's own `Util.equiv` already applies at the top
level. `Util.equiv`'s first line is `k1 == k2` (reference identity)
before any structural comparison, which is exactly why `(let [v (vector
##NaN)] (= v v))` is `true` in real Clojure despite containing a NaN:
identity short-circuits the element walk entirely for the whole vector.
`try_eq_by`'s pruning is that same short-circuit applied one level
deeper -- to shared SUB-structure rather than only to the two top-level
handles being literally the same object -- so a NaN buried in a subtree
two disjoint-at-the-top vectors happen to still share behaves exactly
like a NaN in a vector compared to itself: identity wins, not the
per-element predicate. `##NaN` disjoint pairs (no pointer sharing
anywhere on the path to it, e.g. `(= [##NaN] [##NaN])`) are unaffected
and still compare `false`, measured.

Disjoint (non-`Big`, or `Big` with zero pointer sharing) vector
comparisons are unaffected -- they either fall through unchanged (`Small`
or mixed pairs) or the `Big`/`Big` path degrades to the same per-element
`values_equal` walk, since `try_eq_by`'s own alignment fallback (when
chunk boundaries don't line up) still calls `eq` per non-shared element
pair. Only `values_equal`'s sequential arm is wired this way;
`values_equal_strict` keeps its `uncons`-peeling shape unchanged (see
that function's own doc comment) because it walks the logical sequence
one Value at a time regardless of representation, never touching a
`PVector`'s trie directly, so there is no pointer-identity boundary for
it to prune against in the first place.

## Phase F2 (flow.corpus): known deviations NOT exercised by any corpus line

`tests/conformance/corpus/flow.corpus` (generated against real JVM
`clojure.core.async.flow` v1.9.808-alpha1 via `;;ENGINE jvm-flow`, see
`tools/jvm-flow-runner.clj`) currently has ZERO whitelisted mismatches --
every one of its 47 forms was written to land on the COMMON surface both
engines agree on exactly, per that file's own module-doc "SURFACE
BRIDGING" section. One real conformance bug the corpus DID catch was fixed
directly (`src/builtins/flow.rs`'s `report_error`: the transform-error
map's `:op` value is the literal keyword `:step`, matching upstream's
`impl.clj` `run` loop exactly -- it was previously the non-upstream value
`:transform`).

The following ARE genuine, deliberate deviations discovered while writing
that corpus, but are not represented as table rows above (per this file's
own parsing rule, a row must correspond to an ACTUAL corpus-line mismatch,
and the corpus was written to route around all three rather than assert
on them):

- **`flow/ping`/`flow/ping-proc` timeout-ms calling convention**: mova
  takes it as a positional argument (`(flow/ping fl 1000)`); upstream
  takes it as a trailing kwarg (`(ping g :timeout-ms 1000)`). No single
  corpus form can spell both. Every ping/ping-proc call in flow.corpus
  omits the argument entirely, relying on both engines' own 1000ms
  default -- see `tests/flow_test.rs`'s
  `ping_proc_times_out_absent_reply_while_target_is_busy_in_a_slow_transform`
  for mova-side coverage of the positional form.
- **error-chan `:ex` / ping-reply `:state` shape**: mova's `:ex` is
  `{:message "..."}` (a plain description of the caught `RjError`/panic);
  upstream's is the raw caught `Throwable`/`ex-info` object. Similarly,
  `:state` is each engine's own (structurally different) internal state
  representation. flow.corpus never prints either key -- every
  error-chan/ping-reply scenario extracts only the STABLE keys
  (`:cid`/`:msg`/`:op`, or `:status`/`:count`) via bare keyword access or
  `get-in`, never a whole-map `pr-str`.
- **Emitting to a declared-but-unconnected `:out`**: mova silently drops
  the message (FLOW-DESIGN.md's "Engine semantics": "Unconnected outs =
  nil chan -> drop silently"; pinned by `tests/flow_test.rs`'s
  `unconnected_output_silently_drops`). Upstream's `impl.clj` `send-outputs`
  instead tries `spi/get-write-chan` as a fallback for any output key not
  found with a non-nil value in the proc's own `outs` map, which throws
  `"can't resolve channel with io-id"` for a bare unconnected io-id -- that
  throw is then caught by the SAME per-message `catch` that catches
  ordinary transform errors, so upstream actually reports an error-chan
  entry (and does NOT deliver the message) instead of silently dropping
  it. Not exercised by flow.corpus (no scenario emits to an unconnected
  output) -- mova's existing, simpler, already-documented behavior was
  kept rather than reworked to match this upstream quirk.
- **`flow/pause-proc` on a member of a FUSED chain** (P3, see
  FLOW-DESIGN.md's "Fusion" section): mova may run an unbranching 1:1 run
  of procs on ONE OS thread, in which case pausing any member parks the
  whole run at the next message boundary, so the upstream members' own
  `::flow/count`s stop advancing too (unfused -- and always, upstream,
  which has a go-block per proc -- they would keep running until the
  inter-proc buffer filled, a difference of up to `:buf-or-n` messages).
  Statuses are unaffected: only the paused member reports `:paused`.
  flow.corpus never pauses a single proc of a multi-proc flow (its only
  pause scenario is the flow-wide procs-start-paused one, which is
  identical either way), and the default fusion policy only ever fuses
  runs of mova-only native steps, which no portable corpus form can even
  spell. mova-side coverage:
  `tests/flow_test.rs`'s `pause_proc_mid_chain_pauses_the_whole_fused_run_and_resumes_losslessly`
  asserts BOTH modes' counts explicitly.

## S4 everyday3 (everyday3.corpus): known deviation NOT exercised by any corpus line

- **`pmap` realizes eagerly, ahead of consumption; mova's is fully lazy
  and serial**: measured directly against the oracle (`compat/
  everyday3-probe.clj`'s transcript plus an ad hoc side-effect probe, not
  saved to the corpus -- see below for why): given
  `(let [a (atom 0) r (pmap (fn [x] (swap! a inc) x) [1 2 3 4 5 6 7 8])] (Thread/sleep 200) @a)`,
  real Clojure 1.13.0-alpha6 reports `@a` already `8` -- every element's
  `f` has run -- despite `r` never having been touched. Two real-Clojure
  mechanics compound to cause this: `pmap`'s own body eagerly forces a
  `(+ 2 (.. Runtime getRuntime availableProcessors))`-sized (or, for a
  coll this small, the WHOLE) window of `(future (f %))` cells as part of
  constructing its lazy result, and `map` over a CHUNKED source (a
  vector's chunked seq, 32 elements per chunk) realizes a whole chunk the
  moment the first cons cell is forced -- so an 8-element vector's entire
  `future` window gets created, and starts running concurrently, before
  any consumer ever asks for an element. mova's `pmap` (`core/core.mova`)
  is deliberately just `map` under a different name (see that file's own
  comment) -- fully lazy, single-threaded, one element computed per
  `first`/`rest` step, with `@a` staying `0` until something actually
  walks `r`. For any PURE `f` (the only kind a corpus form can observe)
  the final, fully-realized SEQUENCE is byte-identical either way -- only
  wall-clock parallelism and this realize-ahead-of-consumption timing
  differ, both invisible to `pr-str`. Not represented as a corpus line
  (per this file's own parsing rule, a row must correspond to an ACTUAL
  corpus-line mismatch): the divergence is inherently about TIMING
  relative to an explicit `Thread/sleep`, which the corpus format has no
  precedent for and which would make the golden non-reproducible under
  `bb`/`tools/gen-golden.bb`'s real-JVM-but-still-machine-timing-dependent
  execution.
## RETIRED by S7 (wave-C item 8): the map-entry deviation

Two rows used to sit in the table above -- `classrows-s6.corpus:30`
(`(instance? clojure.lang.IMapEntry (first {:a 1}))`) and
`s6-closer.corpus:24` (`(map-entry? (first {:a 1}))`) -- both answering
`false` where real Clojure answers `true`, both justified by the same
sentence: *mova has no distinct map-entry representation*. `(first {:a
1})` was a plain `Value::Vector`, byte-for-byte the shape of a hand-typed
`[:a 1]`, so no predicate could say `true` for the real entry without also
lying about the literal (`(map-entry? [:a 1])` is `false` on the oracle,
measured). Both rows called themselves "permanent unless mova grows a
distinct map-entry value".

mova grew one. `Value::MapEntry` (see its doc in `src/value.rs`) is a
distinct discriminant carrying the same two-slot `PVec` payload a vector
does, produced at the ONE construction choke point (`Interp::seq_items`,
plus `find`/`subseq`/`rseq`), so an entry is still `=`/`hash`/`compare`-
identical to the equivalent 2-vector while `map-entry?`, `(instance?
clojure.lang.IMapEntry ..)`, `(instance? java.util.Map$Entry ..)` and
`(class ..)` now answer honestly. `crate::types::is_map_entry` and
`builtins::predicates`'s `map-entry?` are both `matches!` on the variant,
never on "2-element vector" -- `[:a 1]` typed by hand is still `false`, as
measured.

Both corpus lines' goldens already carried real Clojure's `true` (goldens
are generated from the oracle, never from mova), so retiring the rows is
the whole promotion: the forms stay in `tests/conformance/corpus/` and now
PASS, and `tests/conformance_test.rs`'s stale-entry assertion -- which is
what flagged this, by failing the build the moment the rows started
conforming -- goes green.

Ground truth for the full behavior matrix (~220 oracle rows across class,
`=`/`hash`, the predicate battery, `key`/`val`, `nth`/`get`/`contains?`,
seq/`rseq`/`count`, `conj`/`assoc`/`pop`/`peek`/`subvec`/`empty`,
`into`/destructuring/print/meta, dot-methods, `reduce`-vs-`reduce-kv`
materialization and `clojure.walk` interplay):
`compat/mapentry-probe.clj` + `compat/mapentry-probe2.clj` and their
`compat/mapentry-oracle-transcript*.txt` transcripts. The rows S7
deliberately did NOT reproduce are listed there and in this branch's
report -- chiefly the SORTED map's entry class, where the JVM leaks its
red-black tree node (`clojure.lang.PersistentTreeMap$BlackVal`) rather
than a `MapEntry`; `map-entry?` is `true` for it on both sides, which is
the property `clojure.walk` and the vendored suite dispatch on.

## S6 boxed-ctor compat veneer: `Float` reports/hashes as `Double`

`(Long. x)`/`(Float. x)`/... (`src/hostclass.rs`'s `construct`) and the
`Short`/`Byte` class rows they needed (`src/types.rs::builtin_classes()`)
are a COMPAT VENEER over one Java-interop idiom the vendored suite spells
out directly (`tests/clojure-suite/vendor/numbers.clj`'s own `(Byte.
Byte/MAX_VALUE)` family) -- NOT a step toward JVM reflection or a Java
object model. mova's real type system is Rust-native: there is no boxed
`Integer`/`Float`/... `Value` variant, by design (see
`CLOJURE-COMPAT-PLAN.md`'s scope decision), so every boxed ctor returns
the exact same `Value` its unboxed counterpart already would --
`(Long. 3)` IS `3`, not a distinguishable "boxed" wrapper around it.

That collapse is invisible almost everywhere (arithmetic, `=`, printing
all agree with the JVM -- see `interop-boxed.corpus`'s ~50 conforming
lines), but it is OBSERVABLE wherever real Clojure code asks a value
"which JVM class are you, exactly": `class`, `instance?` against a
DIFFERENT numeric class than the one that constructed the value, and
`hash` (whose real `java.lang.Float.hashCode` is bit-pattern-based and
genuinely differs from `Double`'s, not merely differently-typed). This is
the FLOATING-WIDTH sibling of the pre-existing "S5 int width" section
above (`Integer`/`Short`/`Byte` all reporting as `Long`) -- same root
cause (one native numeric `Value` per Rust type, not one per JVM box), now
also hit via boxed-ctor construction rather than only via `int`/`short`/
`byte`. `Integer`/`Short`/`Byte`'s OWN `class`/`hash` divergence is left
where the S5 section already put it (unexercised by any corpus line,
policed by `compat/numtower-check.py` instead) -- this task's corpus
deliberately never bare-asserts `(class (Integer. x))` or similar, to
avoid duplicating that pre-existing, differently-policed ledger entry.
`Float` gets its OWN table rows above because `Double`/`Float` did not

## S4/1D (arrays.corpus): array printing is not represented as a table row

`(pr-str (into-array [1 2]))`/`(str (into-array [1 2]))` print
`#object["[Ljava.lang.Long;" 0x<hash> "[Ljava.lang.Long;@<hash>"]` /
`[Ljava.lang.Long;@<hash>]` on BOTH real Clojure and mova (mova mirrors
the shape exactly -- `src/printer.rs`'s `Value::Array` arm -- substituting
its own `Arc` address for the JVM's identity hash). This is not a
deviation in the usual sense: `<hash>` is the JVM's own per-process
`Object.hashCode()`, nondeterministic even real-Clojure-vs-itself across
two separate runs, so no single golden line could ever be "the" correct
answer for either side to assert against, and it is therefore not
representable as a `file:line` table row above (that mechanism whitelists
an ACTUAL corpus-line mismatch against a fixed golden; there is no fixed
golden here to mismatch). `arrays.corpus`'s own header comment documents
the same reasoning and lists exactly which shapes it avoids
(`tests/conformance/corpus/arrays.corpus`); every array-returning form in
that corpus is wrapped in `vec`/`class`/`alength`/`seq`/a boolean
predicate/an explicit `catch`, never bare `pr-str`/`str`/an unwrapped
collection print, so the corpus has zero exposure to this
nondeterminism rather than zero exercise of array printing itself
(printing correctness is still covered structurally: the `#object[...]`
FORMAT match above was verified by hand against the real-Clojure probe
transcript, `compat/arrays-probe-transcript.txt` lines 70-73).

## W3e-3 (`java.math.MathContext`): a map, not a host instance

`(java.math.MathContext. 8)` returns
`{:precision 8, :rounding-mode "HALF_UP"}` -- a plain map -- where real
Clojure returns a `java.math.MathContext` object. Consequences, all
deliberate:

- `(class (java.math.MathContext. 8))` is
  `clojure.lang.PersistentArrayMap`, not `java.math.MathContext`.
- `(instance? java.math.MathContext x)` is `false` for every `x`. The
  class-table row (`src/types.rs`) carries a constant-`false` predicate on
  purpose: mova cannot distinguish this map from any other map with those
  two keys, and answering `true` for `{:precision 1}` would be a lie about
  ordinary data rather than a partial truth about a host object.
- Printing: `*math-context*` prints as that map. This is not new -- it is
  the same divergence `core.mova`'s `with-precision` has carried since S5,
  whose own comment records that real Clojure prints a nondeterministic
  `#object[java.math.MathContext 0x... "precision=4 roundingMode=HALF_UP"]`
  that no corpus line could assert against on either side.
- `java.math.RoundingMode/FLOOR` and its siblings do not resolve at all
  (mova has no `RoundingMode` enum values). mova's ctor accepts the mode
  by NAME instead -- `(java.math.MathContext. 6 "FLOOR")`, or a symbol or
  keyword -- which is the same string `with-precision` already threads to
  `with-precision*`, and which has no meaning on the JVM.

None of this is table-row material: no corpus line asserts any of it (the
`vars.corpus` rows added with this change all assert the *arithmetic*, the
only thing about a math context that is observable in both dialects), and
`(class (java.math.MathContext. 8))` is deliberately not asserted anywhere
for exactly the reason above.

What IS shared, and is corpus-enforced, is that the context reaches the
arithmetic no matter which form installed it -- `with-precision`'s binding
or a bare `(set! *math-context* ...)`. Probe and transcript:
`compat/math-context-probe.clj` / `compat/math-context-oracle-transcript.txt`
(every row identical on both runtimes).
