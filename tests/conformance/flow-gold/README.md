# flow-gold

Semantic-equality corpus proving mova's `clojure.core.async.flow` matches
the original, run from real JVM source. Start with `SPEC.md` for the full
spec (scenario format, comparison semantics, catalog); this file is the
short how-to. `FINDINGS.md` has the semantic facts the corpus has
established so far; `DIVERGENCES.md` has the per-scenario whitelist of
legitimate, documented per-side output differences.

## Layout

```
SPEC.md                 binding spec: format, preludes, comparison semantics, catalog
FINDINGS.md             prose findings, with file:line evidence from both sources
DIVERGENCES.md          whitelist of ;;DIVERGENT scenarios' expected mova output
scenarios/NN-name.mova  portable scenario bodies (same file runs on both sides)
goldens/NN-name.golden  committed JVM output, generated by tools/gen-flow-gold.bb
```

Plus, at the repo root:
```
tools/gen-flow-gold.bb   regenerates goldens/ from the JVM gold implementation
tests/flow_gold_test.rs  cargo test: runs every scenario against the mova binary
```

## Adding a scenario

1. Write `scenarios/NN-name.mova`. Read `SPEC.md`'s "Scenario format" section
   first -- in short:
   - No `require`/`ns` forms. The JVM prelude brings in
     `chan`/`>!!`/`<!!`/`close!`/`timeout`/`flow/*`; mova has all of those
     as global builtins already, so the SAME file runs unmodified on both
     sides.
   - Namespaced keywords always fully-qualified
     (`:clojure.core.async.flow/pid`, never `::flow/pid`).
   - Steps built as `(flow/process (flow/map->step {...}))`.
   - Output is the ONLY thing compared, and must be
     deterministic/cross-run-stable: `(println "RESULT <key> <edn>")`,
     `(println "PASS <invariant>")`, `(println "FAIL <invariant> <detail>")`
     (a committed golden must never contain a `FAIL` line). Never print a
     raw future, Var, channel, exception object, or pause/resume return
     value -- those differ per side (see `SPEC.md`'s "Known per-side
     surface differences").
   - Always `(flow/stop fl)` at the end.
   - Bound every blocking read that could hang (`alts!!` + `timeout` --
     see `FINDINGS.md`'s probe (b) for the portable idiom both sides
     support identically). A scenario that can hang must have its timeout
     path exercised by hand at least once.
   - Optional header directives, as `;;`-comment lines (conventionally at
     the top -- they're inert Clojure comments either way, so their
     literal position doesn't matter to either harness):
     - `;;RUNS n` -- how many times each side runs the scenario (default 5).
     - `;;TIMEOUT-MS ms` -- per-run wall-clock budget (default 30000).
     - `;;DIVERGENT` -- output legitimately differs per side; the golden
       still holds the JVM output, and mova's expected output must be
       recorded in `DIVERGENCES.md` (see that file's own header for the
       entry format).
2. Generate its golden (see below) -- this actually RUNS the JVM gold
   implementation, so it requires a `clojure` CLI and the gold checkout at
   the checkout named by `$FLOW_GOLD_ROOT`.
3. Run the mova-side test (see below) and confirm it's green. If the
   scenario is `;;DIVERGENT`, add its `DIVERGENCES.md` entry FIRST (a
   `;;DIVERGENT` scenario with no entry fails the test with a clear
   message telling you to add one).
4. If you learned a new semantic fact while writing the scenario (not just
   "the scenario passes"), add a prose entry to `FINDINGS.md` with
   `file:line` evidence from both sources, per `SPEC.md`'s "Verification
   protocol for authors".

## Regenerating goldens

Needs a JVM (`clojure` CLI) and the gold checkout on disk. From the repo
root:

```sh
# everything
bb tools/gen-flow-gold.bb

# just one scenario (bare name, name.mova, or a path all work)
bb tools/gen-flow-gold.bb 00-smoke

# point at a different gold checkout
FLOW_GOLD_ROOT=/path/to/other/core.async-flow bb tools/gen-flow-gold.bb
```

Every scenario runs `;;RUNS` times (default 5); ALL runs must produce
byte-identical stdout or generation FAILS LOUDLY for that scenario (rich
diagnostic: run byte-lengths, first divergent pair, output preview) and its
golden is left untouched -- a scenario that isn't stable across JVM runs is
not canonical; fix the scenario (reduce the nondeterminism to a verdict),
don't force a flaky golden. A timing-out or nonzero-exit run is reported
the same way. The script exits nonzero if anything failed, and prints a
summary table at the end regardless.

## Running the mova-side test

No JVM needed -- this only exercises the mova binary:

```sh
cargo test --test flow_gold_test
```

This is ONE `#[test]` function that loops every scenario SERIALLY (not
`cargo test`'s default parallel-per-fn scheduling) -- see the doc comment
at the top of `tests/flow_gold_test.rs` for why (short version: flow
scenarios spin real OS threads per process/inject call, and several
`mova` child processes launched concurrently on one machine can
oversubscribe CPU enough to spuriously blow a scenario's own
`;;TIMEOUT-MS` budget, which is exactly the kind of flakiness this corpus
exists to eliminate).

Each scenario runs `;;RUNS` times against `env!("CARGO_BIN_EXE_mova")`
(the binary Cargo infers from `src/main.rs`, named after the package --
built automatically by `cargo test`); every run's stdout must byte-match
`goldens/NN-name.golden` (or, for a `;;DIVERGENT` scenario,
`DIVERGENCES.md`'s recorded entry instead). A missing golden fails with an
explicit instruction to run `bb tools/gen-flow-gold.bb <name>` rather than
panicking on a raw file-not-found. A mismatch prints a rich per-line diff
(expected vs actual, run index). `DIVERGENCES.md` is kept honest the same
way `../DEVIATIONS.md` is for the corpus lane: an entry whose scenario no
longer actually diverges (mova's output now also equals the golden) fails
as stale, and so does an orphaned entry with no matching `;;DIVERGENT`
scenario.

To run just this crate's flow-gold suite (skipping the rest of the test
suite, useful while iterating on one scenario):

```sh
cargo test --test flow_gold_test -- --nocapture
```

(`--nocapture` surfaces the `println!` summary line and any panic message
directly, since this is a single `#[test]` fn -- there's no per-scenario
test name to filter on with `cargo test <substring>`.)
